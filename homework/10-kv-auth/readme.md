# Контроль доступа к key-value хранилищу

В рамках данного задания вам предстоит реализовать регистрацию, аутентификацию и авторизацию пользователей key-value хранилища. Хранилище для простоты умеет только хранить в памяти строковые ключи и значения, но с одним нюансом. Пространство ключей общее для всех пользователей, но пользователь может прочитать или перезаписать только свои ключи - те, которые он создал первым. Соответственно необходимо уметь идентифицировать пользователей и проверять их права доступа к ключам.

Регистрация и аутентификация пользователей будет реализована через отдельный сервис, который хранит учетные данные и выдает пользователям токены для доступа к хранилищу. Это типичный подход в микросервисной архитектуре, позволяющий вынести в общий сервис базовые функции безопасности. В свою очередь, сервис хранилища должен валидировать токен из запроса пользователя и проверять права на выполнение запрашиваемой операции.

## Интерфейсы

Для доступа пользователей к сервисам будем использовать HTTP. Для простоты в этом задании мы опустим защиту передаваемых по сети данных, но на практике здесь должен быть HTTPS. Для генерации токенов доступа предлагается использовать стандарт [JSON Web Token (JWT)](https://ru.wikipedia.org/wiki/JSON_Web_Token).

### Сервис аутентификации

Сервис выполняет функции регистрации новых пользователей, аутентификации по логину/паролю и проверки существующего токена. Соответственно, сервис имеет три HTTP хэндлера: `/signup`, `/login`, `/whoami`.

#### Регистрация

```
POST /signup
body: { "username": "kek", "password": "kekpassword" }
```

Статусы ответа:
- 200 если новый пользователь успешно зарегистрирован.
- 409 если пользователь с таким именем уже существует.

При успешной регистрации в теле ответа передается JWT-токен, который надо использовать для доступа к хранилищу. Токен должен содержать внутри payload ключ `username` с именем пользователя.

#### Аутентификация

```
POST /login
body: { "username": "kek", "password": "kekpassword" }
```

Статусы ответа:
- 200 если аутентификация прошла успешно.
- 404 если пользователя не существует или передан неверный пароль (хорошая практика использовать единый код, чтобы злоумышленник не смог отличить эти ситуации).

При успешной аутентификации в теле ответа передается JWT-токен, который надо использовать для доступа к хранилищу. Токен должен содержать внутри payload ключ `username` с именем пользователя.

Пользователь может одновременно использовать несколько токенов, созданных через этот хэндлер. Ограничение времени жизни токенов и их удаление мы опустим в этом задании.

#### Проверка токена

```
GET /whoami
Authorization: Bearer {token}
```

Статусы ответа:
- 200 если токен валидный, тогда в теле ответа передается `Hello, {username}`.
- 400 если заголовок `Authorization` отсутствует или имеет неверный формат.
- 401 если токен не валидный (мусор, подписан другой подписью,несуществующий пользователь и т.п.).

### Key-value хранилище

Хранилище поддерживает операции записи и чтения значений по ключу. При этом проверяется право пользователя на выполнении операции с данным ключом. Далее будем считать, что ключ принадлежит пользователю, если он был создан этим пользователем.

#### Запись значения ключа

```
POST /put?key=kek
Authorization: Bearer {token}
body: { "value": "lol" }
```

Статусы ответа:
- 200 если запись успешна (ключа не было изначально, либо он принадлежит пользователю).
- 400 если заголовок `Authorization` отсутствует или имеет неверный формат.
- 401 если токен не валидный.
- 403 если ключ существует, но принадлежит другому пользователю.

#### Чтение значения ключа

```
GET /get?key=kek
Authorization: Bearer {token}
```

Статусы ответа:
- 200 если ключ есть и принадлежит пользователю, тогда в теле ответа передается `{"value": "lol"}`.
- 400 если заголовок `Authorization` отсутствует или имеет неверный формат.
- 401 если токен не валидный.
- 403 если ключ существует, но принадлежит другому пользователю.
- 404 если ключа не существует.

## Требования к реализации

В качестве разновидности токенов предлагается использовать JWT с парой RSA ключей (приватный и публичный). Вам необходимо сгенерировать ключи с помощью OpenSSL и разместить их в папке `solution/auth` в файлах: 
- `private.pem` - приватный (закрытый) ключ,
- `public.pem` - публичный (открытый) ключ.

Хранить "сырые" пароли в сервисе аутентификации нельзя, стандартная практика — хранить хэш пароля (какой-нибудь md5) с какой-то постоянной солью, например в нашем случае именем пользователя.

Писать сервисы можно на любом языке программирования, главное, чтобы:
- код и Dockerfile сервиса аутентификации находились в папке `solution/auth`,
- entrypoint у этого сервиса поддерживал следующие аргументы командной строки:
  - `--private`: путь до приватного ключа,
  - `--public`: путь до публичного ключа,
  - `--port`: порт, на котором будет запущен HTTP сервер,
- код и Dockerfile сервиса хранилища находились в папке `solution/kv`,
- entrypoint у этого сервиса поддерживал следующие аргументы командной строки:
    - `--public`: путь до публичного ключа,
    - `--port`: порт, на котором будет запущен HTTP сервер.

Сейчас в папке `solution` находятся заготовки сервисов на языке Go и соответствующие Dockerfile.

Весь код решения должен размещаться в папке `solution`. При сдаче решения в тестирующую систему отправляется только эта папка, изменения вне неё учитываться не будут.

## Тестирование решения

Тесты, проверяющие решение, находятся в папке `tests`. Тесты написаны как тесты черных ящиков — они делают только HTTP запросы и проверяют, что ответы соответствуют ожидаемому поведению. 

Если вы найдете ошибки или требования из условий, которые не покрывают наши тесты, то вы можете получить за это бонусные баллы. Подробности [здесь](https://forms.gle/GngHr4jWweEKrf4M6).

### Локальное тестирование

Перед запуском тестов не забудьте обновить образы сервисов:

```
docker compose build
```

Запуск тестов в Docker выполняется с помощью команды:

```
docker compose run --rm tests
```

Для локального запуска тестов надо установить зависимости из `tests/requirements.txt` и передать несколько переменных окружения:

```
export JWT_PRIVATE_KEY_FILE="solution/auth/private.pem"
export JWT_PUBLIC_KEY_FILE="solution/auth/public.pem"
export AUTH_SERVER_URL="http://localhost:8090"
export KV_SERVER_URL="http://localhost:8091"

python tests/main.py
```

Для тестирования также можно использовать команду `python3 ../cli.py test`. В этом случае используемое окружение будет аналогично тестирующей системе.
